1. WHAT IS THIS PROJECT
────────────────────────────────────────────────────────────────────────────────

Wizardocs is a domain-specific RAG (Retrieval-Augmented Generation) Q&A system
for ML and LLM documentation. Users ask a question, the system retrieves the
most relevant chunks from an indexed documentation corpus, and GPT-4o-mini
generates a grounded answer with inline citations ([1], [2]) that link back to
the exact source chunk.

The product is positioned as a SaaS tool:
  Free tier  — up to 5,000 indexed chunks, 100 queries/month
  Pro        — $29/month, unlimited chunks + queries, bring-your-own docs
  Team       — $99/month, up to 20 seats, SSO/SAML

Current corpus: LangChain documentation only (3,235 deduplicated chunks).
Roadmap corpus: HuggingFace, MLflow, RAG writing, Vector DB blogs.
Future: users upload their own docs (bring-your-own-docs).

4. PROBLEMS IDENTIFIED
────────────────────────────────────────────────────────────────────────────────

PROBLEM 1: No multi-turn context
  Every /ask call sends only the current question. Follow-up questions like
  "How does that relate to memory?" fail because the LLM has no prior context.
  The frontend holds messages in React state, but nothing is sent to the backend.
  Solution: send last N turns with each /ask call (see Phase 3).

PROBLEM 2: No auth, no user identity
  Anyone can use the app without signing in. "Sign in" goes straight to chat.
  No user_id means quota tracking, history persistence, and multi-tenancy are
  impossible. Everything downstream depends on solving this first.
  Solution: Supabase Auth (see Phase 1).

PROBLEM 3: No persistence -- chat history dies on refresh
  Conversations exist only in React useState. Refresh = all history gone.
  The profile history timeline, sidebar history, and bookmarks have no data
  source. Solution: store chats + messages in Supabase Postgres (see Phase 2).

PROBLEM 4: Quota is advertised but never enforced
  The landing page and signup form both show "5,000 free chunks" and
  "100 queries/month". These are not tracked anywhere. Any user can send
  unlimited queries. Solution: track queries_used per user in DB (Phase 4).

PROBLEM 5: The "5,000 chunks" number is confusing and probably too low
  LangChain docs alone = 3,235 chunks. A single moderately-sized codebase
  or documentation set = 5,000-20,000 chunks. The free tier limit of 5,000
  would block the core "bring-your-own-docs" value prop almost immediately.
  Decision: keep 5,000 for now (it's in the UI everywhere), but the real
  monetization lever is queries/month, not chunk count. Raise chunk limit
  to 25,000 when you launch bring-your-own-docs.

PROBLEM 6: Shared single-tenant index
  Everyone queries the same ChromaDB collection. When bring-your-own-docs
  launches, each user's uploaded chunks must be isolated per user/workspace.
  ChromaDB supports named collections -- one collection per workspace.
  Solution: tag chunks with workspace_id, or use separate collections (Phase 5).

PROBLEM 7: No real confidence score
  ConfidenceMeter in chat.jsx is computed as:
    >= 4 sources -> 0.88, >= 2 sources -> 0.78, else -> 0.62
  This is a rough proxy. Real confidence should come from the reranker's
  top score or from Ragas answer relevancy. Not critical to fix now, but
  document it as a known approximation.

5. WHY SUPABASE -- NOT SQLAlchemy
────────────────────────────────────────────────────────────────────────────────

SQLAlchemy is a Python ORM -- it is NOT a backend solution. It only gives you
a Python layer to talk to a database. You still have to:
  - Choose and run a Postgres/SQLite server yourself
  - Write password hashing (bcrypt)
  - Write JWT generation + validation (python-jose or PyJWT)
  - Implement token refresh logic
  - Build the OAuth flow for Google + GitHub (auth.jsx already has those buttons)
  - Handle session expiry, logout, password reset

Supabase gives you all of the above in one service:
  - Managed Postgres (you define tables, it hosts them)
  - Auth: email/password, Google OAuth, GitHub OAuth -- all built-in
  - JWT issuance and refresh -- automatic
  - Row Level Security (RLS) -- per-user data isolation enforced at DB level
  - Python client: supabase-py (wraps PostgREST + Auth)
  - Free tier: 500MB DB, 50,000 auth users, sufficient for MVP

For this project specifically, Supabase wins because:
  1. Google + GitHub buttons exist in auth.jsx -- Supabase makes these work
     with 3 lines of code, not a full OAuth implementation.
  2. The FastAPI backend does not need auth logic -- it just verifies the JWT
     Supabase issued using their public key (one middleware function).
  3. Chat history tables, user tables, quota tracking -- all go in the same
     Supabase Postgres, queried with supabase-py or raw SQL via psycopg2.
  4. No self-managed database server. Local dev uses the same Supabase
     project as prod. No SQLite -> Postgres migration risk.

When to use SQLAlchemy: if you already have a self-hosted Postgres, need
advanced ORM features (complex joins, migrations with Alembic), or want
zero external dependencies. For an early-stage SaaS app, Supabase is faster.

The backend still uses FastAPI. Supabase is just the auth + database layer.

PHASE 3: Multi-Turn Context (The Memory Problem)
=================================================
Goal: follow-up questions ("what about memory?") work correctly.

The Problem in Detail:
  Currently llm.py sends:
    [system_prompt, {"role":"user", "content": "Context:\n...\nQuestion: Q"}]
  The LLM has no idea what Q refers to when Q is a follow-up.

The Solution -- stateless history injection:
  The frontend sends the last N message pairs along with the new question.
  The backend includes them in the LLM call as conversation history.
  No server-side session storage needed -- messages are already in the DB.

Step 3.1 -- Extend AskRequest schema
  class Turn(BaseModel):
      role:    str    # "user" | "assistant"
      content: str

  class AskRequest(BaseModel):
      question: str
      chat_id:  str
      history:  list[Turn] = []    # last 3 turns = 6 messages max

Step 3.2 -- Update llm.py to accept history
  def generate(query: str, context: str, history: list[dict] = []) -> str:
      messages = [{"role": "system", "content": SYSTEM_PROMPT}]
      for turn in history:
          messages.append({"role": turn["role"], "content": turn["content"]})
      messages.append({
          "role": "user",
          "content": f"Context:\n{context}\n\nQuestion: {query}"
      })
      ...

  IMPORTANT: history goes BEFORE the current question+context.
  The retrieval query remains just `question` -- not the full history.
  This keeps retrieval sharp. Only the LLM call gets history.

Step 3.3 -- Frontend: build history slice before sending
  In chat.jsx send():
      const history = messages.slice(-6).map(m => ({
          role:    m.role === "user" ? "user" : "assistant",
          content: m.text,
      }));
      body: JSON.stringify({ question: q, chat_id, history })

  Why 6 messages (3 turns)?
  - Cost: each turn adds ~300-500 tokens to every API call
  - 3 turns covers 99% of follow-up scenarios
  - Beyond 3 turns, context is usually unnecessary for RAG

  "New conversation" clears messages -> history is empty -> no prior context.
  This is correct. No use_history flag needed -- empty array is the flag.

Step 3.4 -- Update generator.py to pass history through
  def ask(query: str, history: list[dict] = []) -> dict:
      chunks = search_with_rerank(query)   # retrieval: query only, no history
      return generate(query, chunks, history)

Verify: ask "How do agents work?", then ask "How does memory relate to that?"
-> second answer should reference the agents context from the first turn.

7. KEY ARCHITECTURAL DECISIONS (with rationale)
────────────────────────────────────────────────────────────────────────────────

DECISION: No bundler (Vite, webpack) for the frontend
  The entire frontend is served from a single index.html with React loaded
  from the jsDelivr CDN. No npm, no build step.
  Why: this project prioritizes speed of iteration. A bundler would require
  setting up hot reload, build scripts, and import resolution. For vanilla
  JSX served by FastAPI, the CDN approach works and can always be migrated
  to Vite later if the codebase grows.
  Tradeoff: no TypeScript, no tree-shaking, slower initial load on cold cache.

DECISION: ChromaDB (local) over Pinecone/Weaviate
  ChromaDB is file-based and runs locally with no infra. For a single-tenant
  or small multi-tenant workload it is fine. The chroma_db/ directory is
  mounted as a Docker volume.
  When to migrate: if the corpus exceeds ~1M chunks or you need horizontal
  scaling, migrate to Weaviate (self-hosted) or Qdrant. Not Pinecone -- it
  does not support the multi-tenant named-collection pattern needed for BYOD.

DECISION: GPT-4o-mini over Claude or Llama
  Low cost, fast, good instruction following for citation-only prompts.
  The system prompt is strict enough that model choice matters less than
  retrieval quality for grounded RAG.
  Profile settings already has a model selector dropdown (not yet functional).

DECISION: Cohere reranker
  Cohere's cross-encoder significantly improves precision over pure BM25+vector.
  The eval pipeline (Ragas) measures this. Faithfulness improved after adding
  the reranker (documented in commit b16166b).
  Alternative: use a local cross-encoder (bge-reranker-base via sentence-
  transformers). Slower but free. Use if Cohere costs become an issue.

DECISION: RRF fusion (not score normalization)
  BM25 scores (0-15) and vector scores (cosine, 0-1) are on different scales.
  Score normalization introduces a hyperparameter (normalization method) and
  can be gamed by outliers. RRF uses only rank position -- scale-independent,
  robust, no tuning needed. Standard constant k=60 used.

DECISION: Supabase over self-managed Postgres + SQLAlchemy
  See Section 5 above. Summary: Supabase provides auth (email + Google +
  GitHub OAuth), managed Postgres, JWT handling, and RLS in one service.
  Self-managing auth with SQLAlchemy would require bcrypt, python-jose,
  OAuth2 flows, and token refresh logic -- weeks of work Supabase does for free.
  The Google + GitHub buttons already exist in auth.jsx.

DECISION: Stateless history injection (not server-side sessions)
  Each /ask request includes the last N message turns from the frontend.
  The backend is still stateless -- it does not need to look up a session.
  Why not server-side sessions: Redis adds infrastructure, session lookup
  adds latency, and the messages are already in the DB (Phase 2) -- the
  frontend just reads them from its own state.

DECISION: Retrieval query = current question only (not full history)
  Even when history is sent to the LLM, the retrieval step uses only the
  current question as the search query. This keeps retrieval sharp -- embedding
  a paragraph of conversation history produces noisier results than embedding
  a clean question.
  Exception: if the current question is a pure pronoun reference ("that",
  "it", "this"), a query rewrite step would help. Implement if needed.

11. OPEN QUESTIONS / THINGS NOT YET DECIDED
────────────────────────────────────────────────────────────────────────────────

Q: What happens to the shared LangChain index when BYOD launches?
   Option A: shared index always included in every search (augments private docs)
   Option B: users opt in to include it
   Option C: shared index removed, all content must be user-uploaded
   Recommendation: Option A for now. Users get value immediately.

Q: When a user's chat history is loaded from the DB, do we re-render citations?
   The sources_json column stores the source objects. The frontend needs to
   re-hydrate allSources state from this data. Not complex but needs handling.

Q: What is the workspace model? One workspace per user, or team workspaces?
   Current plan: one workspace per user (auto-created on signup).
   Team workspaces come in the Team plan. Implement user = workspace for now.

Q: Should the eval pipeline run against the real /ask API or directly against
   the generator? Currently runs against generator.py directly (faster).
   When auth is added, the eval pipeline will need a service-role JWT bypass
   or a dedicated eval endpoint that skips auth.

Q: Confidence meter -- should it use real reranker scores?
   The top reranker score from Cohere is a real relevance signal (0-1 range).
   Replacing the current proxy (count-based) with reranker top score would
   be more accurate. Low effort, good improvement.
